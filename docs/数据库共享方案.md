# 云手机平台 — 数据库共享方案

## 一、当前状况

### 架构

```
<DB_HOST> (服务器)                   各成员本地 (Windows)
┌─────────────────────┐                  ┌─────────────────────┐
│  Docker Compose     │                  │  SQLite 本地文件     │
│  ├─ PostgreSQL 15   │  ←── 谁也不连 ──→  │  cloud_platform.db  │
│  ├─ Redis 7         │                  │                     │
│  ├─ Backend         │                  │  通过 API 同步设备    │
│  └─ Frontend        │                  └─────────────────────┘
│                     │
│  Redroid 容器       │  ←── ADB ─────── 各成员 ADB 直连
│  (5557~5560)        │
└─────────────────────┘
```

每个成员本地都有一个 `cloud_platform.db`（SQLite 文件），通过 `CLOUD_SYNC_SERVER` 从服务器 API 同步设备列表。但**用户、分组、审计日志**只在各自本地数据库中。

### 问题

| 问题 | 表现 |
|------|------|
| 用户不共享 | 你创建的账号，队友看不到，需要 seed_users 变通 |
| 数据分散 | 每人的审计日志、分组、脚本模板各自独立 |
| 同步脆弱 | 设备同步依赖 API 轮询（30s 间隔），设备状态有延迟 |
| 数据库丢失 | SQLite 文件在本地，误删或重装系统后丢失 |

---

## 二、共享 PostgreSQL 方案

### 目标架构

```
<DB_HOST> (服务器)                   各成员本地 (Windows)
┌─────────────────────┐                  ┌─────────────────────┐
│  Docker Compose     │                  │  vue3 + vite        │
│  ┌─────────────────┐│  ←── 读写 ────→  │  FastAPI 后端       │
│  │  PostgreSQL 15  ││   5432 端口      │  (uvicorn :8000)   │
│  │  (唯一数据源)    ││                  └─────────────────────┘
│  ├─ Redis 7        ││
│  ├─ Backend (服务端)││                  ┌─────────────────────┐
│  └─ Frontend        ││                  │  vue3 + vite        │
│  └──────────────────┘│  ←── 读写 ────→  │  FastAPI 后端       │
│                     │   5432 端口       │  (uvicorn :8000)   │
│  Redroid 容器       │  ←── ADB ─────── └─────────────────────┘
│  (5557~5560)        │
└─────────────────────┘
```

所有人共用一台 PostgreSQL，实现**数据实时共享**。

### 优势

| 方面 | SQLite（现在） | PostgreSQL（方案） |
|------|---------------|-------------------|
| **用户数据** | 每人独立，需 seed_users 补救 | 一人创建，全员实时可见 |
| **审计日志** | 分散在每人本地 | 集中存储，统一查询 |
| **分组/脚本** | 每人独立维护 | 团队共享，一次配置 |
| **设备状态** | API 轮询（延迟 30s） | 直接读写同一库（实时） |
| **数据安全** | 本地文件，误删即丢 | 服务端持久化，不怕丢失 |
| **并发能力** | SQLite 不支持并发写 | PostgreSQL 成熟的多用户并发 |
| **扩展性** | 无法扩展 | 后续可做主从/读写分离 |
| **备份** | 无 | pg_dump / 自动备份 |

### 风险

| 风险 | 应对 |
|------|------|
| 服务器宕机 | PostgreSQL 本身也跑在服务器上，服务器挂了一切都停。不影响——现在服务器挂了一样用不了设备 |
| 多人写冲突 | PostgreSQL 行级锁 + MVCC，开发团队规模（<10 人）完全无感 |
| 网络延迟 | 局域网内 <1ms，比 SQLite 本地 IO 略慢但可忽略 |
| 服务器 5432 暴露 | 已在 docker-compose.yml 中暴露，仅在局域网内，外网不可达 |

## 三、实施步骤

### Step 1 — 每个人改一行配置（1 分钟）

编辑 `backend/.env`，改数据库连接地址：

```env
# 改之前（本地 SQLite）
CLOUD_DATABASE_URL=sqlite+aiosqlite:///./cloud_platform.db

# 改之后（共享 PostgreSQL）
CLOUD_DATABASE_URL=postgresql+asyncpg://<DB_USER>:<DB_PASSWORD>@<DB_HOST>:5432/cloud
```

> 连接信息请按你自己的部署填写：主机 `<DB_HOST>` / 端口 `5432` / 用户 `<DB_USER>` / 密码 `<DB_PASSWORD>` / 库名 `<DB_NAME>`

### Step 2 — 删掉本地数据库

```bash
del backend\cloud_platform.db
```

### Step 3 — 重启后端

```bash
cd backend && python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

首次启动时，seed 脚本会自动在 PostgreSQL 中创建默认管理员；其他成员账号可在「用户管理」页面创建，或用 `CLOUD_SEED_USERS` 预置。

### Step 4 — 重启前端

```bash
cd frontend && pnpm dev
```

## 四、`.env.example` 同步更新

将模板中的数据库配置同步修改，新成员拉代码即用：

```diff
- CLOUD_DATABASE_URL=sqlite+aiosqlite:///./cloud_platform.db
+ # 共享 PostgreSQL（生产/协作模式）
+ CLOUD_DATABASE_URL=postgresql+asyncpg://<DB_USER>:<DB_PASSWORD>@<DB_HOST>:5432/cloud
+ # 本地 SQLite（离线/单机模式，取消下行注释即可切换回去）
+ # CLOUD_DATABASE_URL=sqlite+aiosqlite:///./cloud_platform.db
```

## 五、切换前后对比

| | 切换前 | 切换后 |
|---|--------|--------|
| 用户创建 | 每人本地创建，互不可见 | 任意成员创建，全员即时可用 |
| 团队账号维护 | `.env` 里写 seed_users JSON | 直接 Web 页面增删改 |
| 设备列表 | 30 秒轮询 API | 直读数据库，实时 |
| 审计追溯 | 各看各的 | 所有操作集中可查 |
| 新成员入职 | 5 步初始化 | 改 ADB 路径 → 启动 → 完成 |

---

## 六、回滚方案

如果 PostgreSQL 出问题，随时可切回 SQLite：

```bash
# .env 改回
CLOUD_DATABASE_URL=sqlite+aiosqlite:///./cloud_platform.db

# 重启后端，自动重建本地 SQLite + seed
```

> 注意：切回 SQLite 后数据重新从零开始，团队账号需靠 seed_users 重建。

---

## 七、结论

**建议执行切换。** 一次操作（每人 1 分钟），永久解决用户不共享、数据分散、审计缺失等问题。PostgreSQL 跑在现有服务器上，零额外成本，局域网延迟可忽略。
