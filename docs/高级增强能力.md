# 高级增强能力（商业级网络/防封/秒级刷机/低延迟串流）

本文档用于补充并落地甲方提出的“高端云手机平台”增强要求，目标是在不破坏现有主流程的前提下，扩展出符合跨境电商、挂机场景、机型伪装与高密度并发的能力。

本方案与现有仓库中的 `backend/`、`frontend/`、`deploy/`、`docs/` 结构保持兼容：新增能力以可选增强模块/后台能力的方式接入，不改变主流程的默认运行方式。

## 1. 独享网络与跨境链路（网络层需求）

### 1.1 多外网 IP 绑定
- 支持每个云手机实例绑定独立外网 IP，允许在同一宿主机上按设备维度分配出口 IP。
- 兼容单卡单待（one container = one public IP）和多网卡绑定场景。
- 允许在设备创建或重建时选择网络模式：
  - `shared`：共享网卡
  - `exclusive`：独享网卡/独立 IP
  - `multi-nic`：多网卡模式
- 底层采用 network namespace + veth/iptables + policy routing 的组合方式，避免不同容器间发生出口混用。
- 设备管理 API 增加 `network_mode`、`public_ip`、`gateway`、`proxy_policy` 等字段，保持已有设备创建流程不受影响。

### 1.2 代理协议无缝注入
- 支持在一键刷机阶段自动注入 Socks5 / HTTP 代理链（例如 Apollo、Luminati 等）。
- 启动时自动写入容器内网络配置：
  - system env：`HTTP_PROXY`、`HTTPS_PROXY`、`NO_PROXY`
  - Android / app runtime：代理配置与路由白名单
  - DNS 解析强制走代理/内网 DNS 解析，不允许明文直连
- 通过 `dnsmasq`、`iptables`、`ip rule` + `ip route` 组合实现“代理链路不漏网”，确保 DNS 不泄漏，如：
  - 代理出口只接收指定的网段
  - 非授权流量回落到黑洞/拒绝链
  - Dns leak test 统一校验
- 代理与出口 IP 绑定支持做成策略：
  - 设备级代理
  - 分组级代理
  - 全局默认代理
  - 代理池健康检测 + 自动切换

### 1.3 实施建议
- 后端新增 `network` 模块，可在设备建立、重建、刷机前后执行生命周期钩子。
- 前端管理页增加“网络配置”面板：网络模式、代理协议、代理池状态、DNS 漏网检测状态。
- 对于国内服务器 + 海外业务场景，保留现有 redroid/simulator 运行方式，但允许在真实机网络层插入代理链，以免影响原有演示流程。

## 2. 深度改机与指纹对抗（安全防封需求）

### 2.1 硬件参数彻底随机化
- 每次一键刷机时，不仅修改 `build.prop` 中的品牌、型号、序列号、Android ID 等信息，还会从 Framework 层扩展随机化：
  - Wi-Fi 基站信息
  - 蓝牙 MAC / Wi-Fi MAC
  - 电池状态（Level、Health、Temperature、Voltage 等）
  - 传感器数据（加速度计、陀螺仪、光线、接近、磁场等）
  - Wi-Fi 列表与热点历史记录
  - CPU 架构特征与硬件指纹
- 对设备 fingerprint 生成逻辑做兼容扩展：
  - `vendor` / `brand` / `model` / `device_id`
  - `android_id` / `serial` / `imei` / `sim_slot`
  - `network` / `battery` / `sensor` / `cpu`
- 关键值生成遵循“按设备随机 + 分组隔离”的规则，保证不同虚拟机实例不出现一致性标识。

### 2.2 Anti-Detector / 反检测
- 在高风险场景中，平台支持接入 Magisk + Shamiko，包装 Root 隐藏、权限管理与检测规避能力。
- 采用安全校验链路：
  - Play Integrity
  - SafetyNet
  - device attestation
  - app-level SDK 反检测兼容
- 在设备创建期间，系统会执行完整的“环境合规检查”：
  - Root 隐藏状态
  - SafetyNet/Integrity 错误码
  - 系统 API 调用异常
  - 代理、DNS、时区、语言、屏幕分辨率是否异常
- 若未通过安全认证，平台可阻止该实例接入高风险账号/网站，避免刷机后快速被封。

### 2.3 兼容落地方式
- 这类深度改机能力应作为可选增强模块集成到 Redroid / Android 运行时，而不是破坏原有 simulator 模式；
- 默认演示环境可保留原有 `build.prop` 简单伪造逻辑，但在商业用户场景开启高级防封能力时，则启用 Magisk/Shamiko 及 attestation 方案。

## 3. 秒级一键刷机（资源管理需求）

### 3.1 销毁重建 < 5 秒
- 新建/刷机逻辑不采用真实镜像拉取与重建的慢路径。
- 采用分层存储（如 OverlayFS / Btrfs 快照 / copy-on-write）方案：
  - `/data` 只写增量层
  - 恢复出厂设置只消除增量层，而不重建主文件系统
  - 设备恢复时间控制在 5 秒内
- 对每台云手机做独立快照，销毁后可直接从快照恢复，显著减少 I/O 和启动时间。

### 3.2 预热机制（Pre-warm）
- 平台后台预先保留 5–10 台全新、未绑定状态的待用容器。
- 用户点击“一键刷机”时，直接分发已预热实例，避免等待冷启动。
- 旧实例异步销毁，确保用户体验达到“零等待刷机”。
- 前端 UI 增加“预热池”状态展示，便于管理和运维观测。

### 3.3 后续落地建议
- 扩展 `Device` 模型字段：`state`、`warm_pool`、`recycle_after`、`last_reset_at`。
- 在 `backend` 中新增 `factory_reset` / `prewarm` 任务队列，保证和当前任务调度模块兼容。

## 4. 高密度并发与超低延迟串流（体验层需求）

### 4.1 WebRTC 协议栈
- 商业级场景应优先使用 WebRTC，而不是传统 `WebSocket + Canvas` 拼接。
- 实时流采用 H.264 / H.265 硬编码，减少 CPU 与带宽占用，提升帧稳定性。
- 控制链路与视频链路分离：
  - 输入事件（鼠标/键盘）链路低延迟
  - 视频帧链路按质量/分辨率自适应
- 鼠标点击到画面响应的端到端延迟目标：50ms 以内。

### 4.2 高密度并发能力
- 在双路 AMD 9654 + 2 张 NVIDIA A16 的高端配置下，单台服务器目标支持 120–150 路 720P/60fps 云手机并发。
- 通过编码器、GPU 资源池化、显存调度、帧缓存控制、按需转码等方案实现密度提升。
- 运行时要具备 CPU / GPU / 显存 / 网络占用的平滑扩容和保护机制，避免单机“瞬时崩盘”。

### 4.3 批量接入与扩展建议
- 在 `ws-scrcpy` / `scrcpy` / `WebRTC` 三种方案之间，保留兼容能力，默认优先支持 WebRTC 生产模式。
- 在管控端中增加带宽/码率/分辨率/帧率控制策略，使不同业务优先级可动态调度。
- 管理页增加“并发密度统计卡”与“网络抖动/延迟”指标，便于监控站点稳定性。

## 5. 兼容性说明

上述增强能力是“商业级扩展模块”，它们的设计目标是：
- 不破坏现有 demo 主流程；
- 不迫使老用户迁移到全新平台；
- 以可选增强、后台灰度和策略开关的方式接入。

默认状态下，原有功能（登录、设备管理、群控、脚本、预览、App 端、iOS 皮肤、报表等）保持不变；在真实高风险环境中再按需启用网络隔离、防封改机、秒级刷机和 WebRTC 生产能力。

## 6. 建议的落地顺序

1. 网络层：独享 IP + 代理链 + DNS 漏网控制
2. 安全层：随机化硬件参数 + Magisk/Shamiko + Integrity 验证
3. 刷机层：OverlayFS/Btrfs 快照 + 预热池 + 出厂快速重置
4. 串流层：WebRTC 上线 + H.264/H.265 编码 + 低延迟优化
5. 监控层：并发密度、CPU/GPU/内存、流媒体中断与安全审计

以上能力可以作为项目的后续增强路线图，逐步叠加到仓库当前已有的 Demo 能力之上。
